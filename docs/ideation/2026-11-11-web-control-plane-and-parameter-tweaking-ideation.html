Codebase Context

Ideation is grounded in the live modest-bose architecture running 24/7 on Raspberry Pi 5 (scripts/trading-bot.service) against Trading 212 Invest spot 3x/5x leveraged ETPs, plus institutional learnings captured under docs/solutions/ and prior art from external dynamic-strategy platforms.

Web Surface & Auth Bottlenecks

  • trading_system/dashboard/server.py (ThreadingDashboardServer, SSEBroadcaster) serves static signals_dashboard.html (815 lines) plus read routes (/api/data, /api/stream) and only one write route (/api/panic).
  • do_POST (server.py:1791-1848) skips token verification if PANIC_FLATTEN_TOKEN is blank, allows Access-Control-Allow-Origin: *, and instantiates separate Trading212Client, RiskManager, and PositionMonitor objects outside the live orchestrator lock.

Config Caching & Parameter Drift

  • Settings dataclass (trading_system/config.py:42-191) loads .env once at startup; ~15 settings bind onto self.* in RiskManager.__init__ (risk_manager.py:80,100-125), DirectionalTrendStrategy.__init__ (directional_trend.py:46-50), and PositionMonitor.__init__ (position_monitor.py:132).
  • Components mix cached attributes with direct getattr(settings, ...) reads, creating split-brain behavior if config changes mid-run without cycle latching.

Extensibility & Safety Invariants

  • StrategyRegistry.register_class() (registry.py:34-39) supports dynamic registration and StrategyImprovementAgent defines 11 REQUIRED_INDICATORS plus 4 market regimes and verify_parameter_adaptation(), yet only DirectionalTrendStrategy is loaded and rules live in Python.
  • CURATED_3X_PAIRS and GBX_TICKERS span ~1,800 lines of hardcoded Python in leveraged_universe.py:50-1863.
  • Trading 212 execution imposes 1 req/sec pacing via _global_rate_lock = threading.RLock() (trading212_client.py:193), 50.5s metadata intervals (L200), single GTC stop orders, atomic JSON state in active_trades.json, and local SQLite caching (data/candles.db).

Past Learnings & Prior Art

  • Docs/Solutions: Never mask null P&L fields in UI; merge live fills in build_dashboard_data(); treat Trading 212 broker metadata as ground truth before mutating stops or GBX denominations.
  • Prior Art & Analogies: Envoy xDS generation-swapped config; Pydantic schema-driven UI; OpenAlgo Flow / Composer.trade / Deriv DBot JSON AST rule engines; Airbus Flight Envelope & IEC 61511 SIS admission clamps; OWASP APTS two-phase kill switch; shadow dry-run diffing.

1. Dual-Plane Epoch ConfigBus & Schema-Driven Control Gateway

ID 1 live-parameter-tweaking-and-schema-sync Confidence 94% Complexity Medium
Description
Replace startup-only self.* parameter caching across engine components and ad-hoc HTTP POST handling with an Envoy-inspired dual-plane ConfigBus paired with a fail-closed single-orchestrator command gateway. Annotate Settings fields in trading_system/config.py with calibration metadata (group, unit, min/max bounds, step, mutability tier: hot_tick, next_scan, restart_locked) exposed via /api/manifest and /api/schema/config so any new Python knob renders its own validated web widget with zero HTML duplication. Submitted mutations pass through an authenticated command inbox into the single live Orchestrator (sharing PositionMonitor locks and _global_rate_lock), persist atomically to config_overrides.json, mint an immutable ConfigSnapshot(generation_id) swapped strictly at scan-cycle and monitor-tick boundaries, and stamp newly opened positions in active_trades.json with their entry config_epoch_id so open trades do not suffer retroactive stop-out whiplash unless explicitly migrated.
Basis
direct: trading_system/agents/risk_manager.py:80,100-125 binds ~15 settings onto self.* at __init__ (including a default atr_sl_multiplier: float = 1.5 vs config.py:111's 2.2); trading_system/strategies/directional_trend.py:46-50 caches self.min_adx_trend; trading_system/execution/position_monitor.py:132,1315 mixes cached self.pure_tsl_mode with runtime settings.SESSION_CLOSE_CUTOFF_UTC; trading_system/dashboard/server.py:1791-1848 skips auth when PANIC_FLATTEN_TOKEN is empty and instantiates fresh uncoordinated Trading212Client / PositionMonitor instances per request. external: Envoy xDS generation-swapped config bus, Pydantic model_json_schema() UI reflection, and Modular Audio DSP bar-boundary parameter latching.
Rationale
Every downstream web tweaking capability depends on fixing the init-time self.* split-brain and removing concurrent in-handler broker instantiation. Unifying schema reflection, fail-closed command routing, and cycle-boundary epoch snapshots eliminates Raspberry Pi restarts and guarantees that new Settings fields immediately become safe, synchronized web controls.
Downsides
Requires refactoring worker constructors to consume apply_snapshot() hooks cleanly, defining explicit epoch-migration semantics for open positions, and requiring a configured mutation token before enabling LAN write access.
Conceptual separation between web metadata/command intake and boundary-latched worker snapshots.

2. Self-Describing Rule AST Cartridges, + Add Parameter Studio & Allocation Matrix

ID 2 dynamic-extensibility-and-rule-composition Confidence 91% Complexity High
Description
Directly enable adding both new parameters and new trading strategies from web pages without touching Python source files or exposing unsafe eval(). Pair a browser + Add Parameter Studio persisted to dynamic_parameters.json (exposed transparently through settings.get_param() / getattr) with self-describing JSON Abstract Syntax Tree Strategy Cartridges supporting composable predicates (ALL, ANY, WEIGHTED_VOTE, THRESHOLD, CROSSOVER, REGIME_SWITCH) over the 11 canonical series in REQUIRED_INDICATORS and bundled custom parameter definitions. Saving a validated cartridge dynamically registers a DeclarativeStrategy(BaseStrategy) class via StrategyRegistry.register_class(), auto-generates live UI sliders, streams an in-memory Live Universe Sieve Truth-Table showing per-gate pass counts on cached universe_metrics (pinpointing STARVED gates at zero broker API cost), and stages rollout via a multi-strategy Capital Allocation Matrix pre-checked on synthetic candles before LSE open.
Basis
direct: trading_system/strategies/registry.py:34-39 already implements StrategyRegistry.register_class(cls, name, strategy_cls); trading_system/agents/strategy_improvement_agent.py:45-57,112-160 standardizes REQUIRED_INDICATORS and STARVED zero-yield diagnostics; trading_system/agents/risk_manager.py:743-744 uses dynamic getattr(settings, ...) lookups; trading_system/config.py:126 restricts live runs to scalar ACTIVE_STRATEGY; trading_system/data/trading212_client.py:2016 provides offline deterministic synthetic candles. external: OpenAlgo Flow DAG-to-JSON compilation, Composer.trade hierarchical ASTs, and Deriv DBot embedded parameter manifests.
Rationale
Unifies creating custom parameters, authoring new signal rules, explaining filter bottlenecks, and phasing capital allocation into one safe declarative workflow anchored onto existing registry and indicator contracts—eliminating code deployments for strategy iteration.
Downsides
Non-standard primitives outside REQUIRED_INDICATORS (new external API feeds or custom microstructure transforms) still require Python adapters; multi-strategy execution needs clear portfolio arbitration under MAX_SECTOR_POSITIONS and MAX_PORTFOLIO_BETA_HEAT.
Conceptual workflow turning web-authored parameters and rule ASTs into live allocated strategies without editing Python files.

3. Immutable Flight-Envelope Admission Kernel, 4-Tier Kill Switch & Soak Watchdog

ID 3 safety-envelopes-dry-run-and-live-guardrails Confidence 92% Complexity High
Description
Isolate capital preservation from browser configurability by placing an unbypassable Hard Flight-Envelope Kernel between web requests and execution. Startup environment constants anchor constitutional limits—maximum per-trade risk, MIN_SL_PCT/MAX_SL_PCT stop bounds, MAX_LEVERAGE ceiling, mandatory single GTC stop-order invariant, _global_rate_lock pacing floor, and explicit two-step USE_LIVE arming—inside a Kubernetes-style Mutating/Validating Admission Controller that clamps or rejects unsafe web payloads regardless of frontend bugs. Replace server.py's exposed /api/panic endpoint with fail-closed token/TOTP auth (compatible with plain-HTTP Raspberry Pi LANs where WebAuthn fails without HTTPS) driving a two-phase 4-Tier Kill Switch (L1 Entry Halt, L2 Tighten Stops to Breakeven, L3 Graceful Close, L4 Rate-Limited Panic Flatten) strictly through the live Orchestrator lock. Add policy-triggered TTL Leases for temporary overrides, Telegram/Discord diff receipts with 1-tap rollback, and a Dead-Man's Soak Watchdog that auto-reverts if DAILY_MAX_DRAWDOWN_PCT or scan errors spike post-promotion.
Basis
direct: trading_system/dashboard/server.py:1791-1843 skips authorization if PANIC_FLATTEN_TOKEN is empty and spawns detached broker clients bypassing the live lock; trading_system/data/trading212_client.py:193,467,510 defines process-wide _global_rate_lock = threading.RLock(); trading_system/agents/risk_manager.py:81-82,228 clamps stops between min_sl_pct and max_sl_pct; trading_system/config.py:54,60-63,145,156-157,168-170,186 defines hard caps, circuit breakers, and Telegram/Discord notifiers; scripts/trading-bot.service:1-23 runs unattended 24/7 via systemd. external: Airbus Fly-By-Wire Normal Law, IEC 61511 Safety Instrumented Systems (SIS vs BPCS), Kubernetes Admission Webhooks, OWASP APTS two-phase kill switch.
Rationale
Allowing parameter and rule writes on a 24/7 leveraged trading bot is hazardous without structural limits no HTTP route can disable, LAN-compatible fail-closed authentication, graduated non-destructive exits, and automatic soak-window rollback when operators close the browser.
Downsides
Widening constitutional ceilings intentionally still requires SSH/.env updates; TOTP or bearer token setup introduces initial onboarding friction; aggressive soak auto-revert thresholds risk unnecessary churn in spiky opens if tuned too tightly.
IEC 61511 / Avionics separation between mutable web inputs and immutable startup risk laws, paired with watchdog auto-revert.

6. Two-Stage Pre-Flight SQLite Replay & Zero-Quota Live Shadow Twin

ID 6 safety-envelopes-dry-run-and-live-guardrails Confidence 88% Complexity High
Description
Gate parameter adjustments and newly authored strategies behind a two-stage empirical qualification workflow (Draft -> Pre-Flight Replay -> Shadow Live -> Promote) consuming zero additional Trading 212 API quota. In Stage 1 (Pre-Flight Replay), clicking "Preview Impact" runs BacktestEngine against locally cached SQLite candles (CANDLE_DB_PATH), logged executions (trades.jsonl), and verify_parameter_adaptation() to surface historical win-rate, profit-factor, and peak drawdown deltas before saving. In Stage 2 (Live Shadow Twin), candidate configurations evaluate passively inside Orchestrator on the exact universe_metrics tick stream already fetched by production, streaming virtual fills, simulated GTC stops, and real-spread slippage diffs over SSEBroadcaster into a side-by-side Live vs Shadow ledger until the operator clicks Promote.
Basis
direct: trading_system/config.py:160-161,174,188 configures local SQLite persistence (CANDLE_DB_PATH = "data/candles.db", TRADES_LOG_PATH = "trades.jsonl"); trading_system/orchestrator.py:1314-1320 integrates BacktestEngine; trading_system/agents/strategy_improvement_agent.py:65-68,141-147 ingests shared universe_metrics per cycle and runs verify_parameter_adaptation(); docs/solutions/logic-errors/broker-history-sync-5x-leverage-and-sqlite-candle-cache.md documents local candle cache reliability. external: Composer.trade pre-flight dry-run backtests and production shadow-traffic diffing.
Rationale
Catches brittle parameter values offline via cached SQLite replay and validates real intraday European ETP bid-ask spread behavior live in shadow mode before committing capital, without multiplying broker API load.
Downsides
Offline SQLite replay skips bars absent from candles.db unless pre-warmed (avoiding blocking yfinance network stalls during UI previews); running multiple simultaneous Shadow Twins needs a cap on Raspberry Pi memory and CPU.
Dual empirical qualification: cached historical check plus zero-API-cost live shadow execution prior to promotion.
